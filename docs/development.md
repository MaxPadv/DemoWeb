# Правила разработки HR-портала (регламент)

Документ для онбординга/новой сессии. Здесь — как устроено и как править проект,
чтобы не разбирать стек заново. Фичи — отдельно в `docs/<фича>.md`.

## Обязательно (правило №0 — перед началом ЛЮБОЙ разработки)

1. **Свериться с этим регламентом** (`docs/development.md`) и с роль-моделью/фиче-доками
   (`docs/<фича>.md`) **до** начала разработки/кодинга. Не начинать вслепую.
2. Следовать процессу: **постановку + RED-тест пишет ассистент**, реализацию — **omp**
   (для кодинга), проверка после omp — всегда. Некодинг/ресёрч/ревью — delegate_task.
3. **Перед отправкой задач в кодирование — согласовать декомпозицию (срезы TDD) с пользователем.**
4. При изменении фич — обновлять регламент и фиче-доки (держать актуальными).
   При изменении схемы БД (таблица/колонка/индекс/сид) — обновлять **`docs/database.md`**.
5. Роли субагентов (QA/DevOps/ревьюер/кодер) — см. раздел «Роли, субагенты».
6. **Задачи субагентам (omp) — атомарные и независимые**: каждая касается СВОЕГО набора файлов,
   не пересекается с другими, чтобы агент не завис надолго. Крупную фичу резать на мелкие
   независимые задачи и отдавать их **последовательно** (по одному, не параллельно), по
   требованиям из постановки. Не верить отчёту агента — проверять сборкой/тестами после.

## Что это за проект

Демо-прототип HR-портала: единое окно (shell, React 18 + webpack 5 Module Federation),
в которое HR-сервисы подключаются как независимые микрофронтенды-remotes + FastAPI API.
Каждый сервис — своя пара «frontend-remote + backend», собирается отдельно, запускается
через docker compose; единая точка входа — API-шлюз nginx (:8090). Подробно — `docs/deployment.md`.

- Технологии (2026-10-23): Keycloak 37k, Kong 44k (альт. APISIX 17k), PostgreSQL,
  Module Federation 2.0. Отклонены single-spa (затух), qiankun, Backstage, Frappe/OrangeHRM (монолиты).
- Прод-цель — 10k пользователей; в этом репо — прототип в **одном контейнере**
  (nginx-шлюз + 2 uvicorn-воркера + статика remotes + один Postgres). Прод-контур (k8s/HPA,
  Kong, Keycloak, БД-на-сервис, Redis) — вне этого демо.

```
│   ├── vacations/

│   │   ├── backend/    #   Бэкенд «Отпуска» (FastAPI /api/vacations*, /department*, пересечения)
│   │   └── tests/      #   тесты сервиса (через шлюз)
│   └── structure/
│       ├── frontend/   #   Remote «Структура компании» (publicPath /mf/structure/)
│       ├── backend/    #   Бэкенд «Структура» (/api/structure*)
│       └── tests/      #   тесты сервиса
├── shared/             # общее: auth (X-User/X-Roles), db-пул, overlap (find_overlaps), структура-данные
│   └── tests/          #   юнит-тесты общей логики
├── e2e/                # дымовые Playwright-смоки (образ sogaz-auto-chrome, Nexus)
├── platform/gateway/   # API-шлюз nginx: /api/<key>/* → бэкенд, /mf/* → фронт

└── docs/               # постановки и as-built доки по фичам
```

## Как подключить новый сервис (если нужен новый remote)

1. Копия `services/<svc>/` (frontend + backend): свой `name`, `exposes`,
   `publicPath: /mf/<service>/`; свой бэкенд-модуль (роутер + `init_<svc>(pool)`).
2. Запись в реестре `services.json` (поле `remote`; в k8s — ConfigMap).
   Shell подхватывает remote в рантайме — пересобирать shell не нужно.
3. Добавить сервис в `docker-compose.yml` (свои контейнеры `frontend-<svc>`, `backend-<svc>`).
4. Прописать маршруты в `platform/gateway/nginx.conf` (`/api/<svc>/*` → бэкенд, `/mf/<svc>/` → фронт).

  - pip → `https://nexus.sogaz.ru/repository/pypi-group/simple/`; `--trusted-host nexus.sogaz.ru`.
  - apt → `https://nexus.sogaz.ru/repository/apt-proxy-deb.debian.org-bookworm/` `[trusted=yes]`.
  - Самоподписанный сертификат nexus.sogaz.ru → не доверять, ставить флаги выше.

## Ветки и слияние

- Каждая фича — **две ветки**: `feature/<фича>-backend` и `feature/<фича>-frontend`.
- В одном репозитории фронту нужны бек-источники → **ребейзить `feature/<X>-frontend`
  на `feature/<X>-backend`** перед сборкой. НЕ разрабатывать фронт на чистом master.
- Слияние в `master` (ff) после ревью: `git checkout master && git merge --ff-only feature/<X>-frontend`.

## TDD и omp

- **Постановку + RED-тест пишет ассистент**, реализацию — omp (`omp --cwd="$(pwd)" --print "..."`,
  бэкграунд; ожидаемое время до ~900с / 15 мин, при зависании — резать и гонять срезы по одному).
- **omp не выпускать на git-операции** (инцидент с потерей `tests/`). omp только пишет код;
  коммитит/ветки — ассистент.
- Тесты в `services/<svc>/tests` и `shared/tests`, запуск из корня:
  `python3 -m pytest services shared/tests -q` (нужен поднятый стек через шлюз).
- **Проверка после omp всегда**: TS-ошибки ловятся только на `docker compose up --build`
  (omp часто пропускает импорт/типы). Подтверждение фичи в образе:
  `"$DEXE" exec hr-main-hr-portal-1 sh -c "grep -ro 'ТЕКСТ' /usr/share/nginx/html/mf/vacations/__federation_expose_App.js"`.

## Данные — чистота обязательна

- Заявки **append-only** (тесты добавляют, не удаляют) → за сессию накапливается шум и ломаются
  лимиты. Перед прогоном: `DELETE FROM vacations;` + `"$DEXE" restart hr-main-backend-vacations-1`
  → пересид 4 сид-заявок.
- **Все тестовые и сид-данные — только 2027** (уточнение пользователя). Ротацию годов в
  фикстурах не делать.
- **Лимит 28 дней/сотрудник/календарный год** (сумма по всем заявкам) — 422 при превышении.
  Из-за накопления — короткие тестовые отпуска (1 день по умолчанию в фикстуре `make_vacation`).
- **Дедуп**: одинаковые `(employee, start, end)` учитывать один раз в `find_overlaps`, иначе
  накопленные дубли дают дублирующиеся строки пересечений.
- Очистка накопленного: `./scripts/cleanup_test_data.sh` (удаляет `vacations WHERE comment LIKE 'auto-%'`).
- `POST /api/vacations` отклоняет (422) любую заявку с `start`/`end` вне 2027.

## Демо-персонажи (роль-модель + auth)

Управление доступом — **ролями на сотрудниках** (`employees.role`), не по имени: переназначил
роль → изменилась видимость/управление. Детально — `docs/auth-service.md`, роль-модель —
`docs/role-model-vacation-planning.md`.

- **`top`** — видит свои + подчинённых (всё дерево; для корня = все), управляет всеми, создаёт свои.
- **`head`** — видит свои + подчинённых (дерево), согласует отпуска подчинённых (в т.ч. «вышестоящий
  за нижестоящего»), создаёт свои.
- **`employee`** — создаёт **только свои**, без согласования (видит коллег отдела, read).

### Версии сервисов (политика отображения)

- Свой version (semver) у каждого сервиса (frontend-remote + его бэкенд); в CI/CD — из тега/артефакта.
- Версия показывается **внутри страницы самого сервиса**; **не** в левом меню, на экране выбора
  сервисов и в переходах. Во вкладках может быть несколько микрофронтов — версия подписывается у
  конкретного сервиса. Подробности и целевая архитектура независимых сервисов — `docs/deployment.md`.

## Web QA — e2e смоуки (Playwright)

Дымовые тесты веб-оболочки (`e2e/smoke/test_smoke.py`, 8 сценариев: shell, выбор сервиса,
запланировать отпуск, back/структура, выход, выбор периода, старт не с выходного, подсветка+сброс)
гоняются **в
образе `nexus.sogaz.ru/sogaz-auto-chrome:1.6`** — в нём уже собран браузер
(Chromium в `/root/.cache/ms-playwright`). Именно так делают сайтовые автотесты
СОГАЗ (`sogaz_auto/autotest-projects/site-2.0-autotests`, общий CI-шаблон из
`pipes::.gitlab-ci-web-template.yml`). Внешние CDN для скачивания браузера
заблокированы, поэтому браузер и зависимости берём из корпоративного контура
(Nexus: `pypi-group` для pip, Docker-реестр Nexus для образа).

Запуск — в контейнере на сети compose, против шлюза по имени сервиса `gateway`
(не `localhost`). Команда и пояснения — в `e2e/README.md`.

- На локальном WSL браузер не скачивается (`playwright install` — внешний CDN
  таймаутит), a Windows-браузер (Яндекс/Edge) из WSL-Playwright не запускается
  (loopback-изоляция WSL2). Поэтому — только через образ `sogaz-auto-chrome`.
- В `e2e/conftest.py` Chromium стартует с `--ignore-certificate-errors`
  (как в `browser_config.yml` референса) — иначе при самоподписанных
  сертификатах внутреннего контура консольная ошибка `ERR_CERT_AUTHORITY_INVALID`
  валит тесты на ловле ошибок консоли.

## Питфоллы (проверенные замечания)

- **Нативный `<input type="date">` не ограничивает список годов** через `min/max` (Chrome всё
  равно показывает 2026/2028 в пикере). Финальное решение — оставить date-input с
  `min="2027-01-01" max="2027-12-31"` (бэк отсекает 422); селекты месяц+день отклонены
  пользователем как «выглядит хуже». Убрать другие годы из пикера можно только JS-датапикером.
- **Кнопка развернуть/свернуть**: если видимость завязана на «осталось месяцев»
  (`remainingMonths > 0`), при полном раскрытии счётчик = 0 и «Свернуть» исчезает. Условие —
  `(expanded || remaining > 0)` или всегда рисовать кнопку.
- Календарь отпусков размещаем между «Новая заявка» и «Заявки» (читаемость — просьба пользователя).
- `webpack` закреплён на 5.111.1 (`overrides` в корневом package.json) — выше не собирается
  `@module-federation/enhanced`.

## Роли, субагенты и сопровождение регламента

- **Основная роль ассистента** — Технический менеджер (скилл `techgovernance`): управляю и
  **оцениваю** остальных ролей-субагентов; распределяю задачи, принимаю решение по результатам.
- **Перед отправкой задач в кодирование (omp/субагенты) — согласовать с пользователем**:
  показать, как зафиксирована декомпозиция постановки (срезы TDD) и что конкретно уйдёт на
  субагентов. Только после подтверждения — отправлять. Не запускать кодинг вслепую.
- **Планировать запуск субагентов для экономии контекста**, не только для разработки: ресёрч
  (`web_search`/`web_extract`), анализ, написание больших доков, OCR макетов — можно отдавать
  субагентам. Для некодинга субагент через **delegate_task** (не обязательно omp).
- **omp** — кодовый агент для реализации задач (постановку/RED тест пишет ассистент, omp — код).
- Доступны 2 модели (deepseek, qwen) и **OCR чандра** (`proxy-ai.sogaz.ru/h100-chandra/...`) —
  для распознания макетов/скриншотов, когда vision_analyze недоступен.
- **Регламент (`docs/development.md`) и фиче-доки обновлять по мере изменения фич** — держать
  в актуальном состоянии, чтобы следующая сессия не разбирала стек заново.

### Роли субагентов (оркестрация, по скиллам Hermes)

| Роль субагента | Скилл(ы) | Что делает | Запуск |
|---|---|---|---|
| QA автоматизатор Web | `qa-web-automation` | веб-автотесты (Playwright), e2e/смоки, флейк-анализ | delegate_task |
| QA (аудит автотестов) | `qa-autotest-audit` | аудит покрытия и качества автотестов | delegate_task |
| DevOps | `devops-engineer`, `sre-devops`, `secrets-credential-engineer` | инфраструктура, CI/CD, секреты, релизы, наблюдаемость | delegate_task |
| Независимый ревьюер | `code-reviewer`, `requesting-code-review` | ревью кода/архитектуры без контекста (свежий взгляд) | delegate_task |
| Кодер | omp (CLI-агент) | реализация задач (постановку+RED-тест пишу я) | omp --print |

- Ревью — всегда **независимый** субагент (свежий контекст, не мои гипотезы).
- Для кодинга — **omp**, не delegate_task (у omp свой изолированный процесс).
- Аудит/большие доки/ресёрч/OCR — delegate_task (не обязательно omp).

## Документация фич

- Каждая фича — `docs/<фича>.md`: постановка/декомпозиция (TDD-срезы) → после реализации
  обновляется до финального «as-built» состояния с замечаниями и вопросами для расширения.
