# Технический долг (tech-debt) HR-портала

Незакрытые/отложенные пункты по итогам code review (независимый ревьюер) и планам
архитектуры. Обновлять по мере выполнения.

## Из ревью (отложено осознанно)

- **Пагинация на department-эндпоинтах** (`/api/vacations/department`, `/department/overlaps`,
  `/department/calendar`): тянут все строки отдела без limit/offset; `find_overlaps` — O(n²).
  Добавить limit/offset (как в `list_vacations`) или окно по датам.
- **Конкуренция в 28-дневном лимите**: `SELECT SUM(...)` затем `INSERT` не атомарны — два
  одновременных создания для сотрудника/года могут превысить 28. Сделать атомарно
  (`INSERT ... SELECT ... WHERE сумма+days <= 28` или транзакция с блокировкой).
- **Платформенные ручки прибиты к сервису отпусков** (`platform/gateway/nginx.conf`):
  `/api/me`, `/api/services`, `/api/health` → backend-vacations. Вынести на выделенный
  platform-сервис/конфиг-мапу + автообнаружение сервисов (без ручной правки nginx).
- **`shared/` продублирован в каждом образе** (точка рассинхрона): при разделении на отдельные
  репозитории перейти на версионируемый пакет `hr-portal-shared` (Nexus pypi) /
  `@hr/shared` (npm) с фиксацией версий.
- **Фиксация версий сборки**: образы (`python:3.12-slim`, `node:20-alpine`, `postgres:16-alpine`,
  `nginx:alpine`) и pip-зависимости без `==X`/digest — сборки невоспроизводимы. Зафиксировать.
- **Сборка фронтендов тяжёлая и общая**: контекст = корень репо, каждая сборка — полный
  npm install всех воркспейсов. При переходе на отдельные репо — изолированная сборка на сервис.
- **Хардкод `2027` в трёх слоях** (бэкенд vacations + фронтенд): при смене года править в N местах.
  Вынести в конфиг/параметр.
- **Креды БД в plaintext** (`docker-compose`, shared/db.py deфолт): для демо ок, в прод — секреты.

## Найденные баги в пилоте

- ✅ **ИСПРАВЛЕНО** — офф-бай-один на календаре в не-UTC таймзоне (MSK/UTC+3): `datesInRange()`
  теперь формирует `YYYY-MM-DD` из локальных компонент (не `toISOString`).
  Было: даты строились через `new Date(iso+'T00:00:00')` + `cur.toISOString().split('T')[0]`,
  `toISOString` переводил в UTC → при UTC+3 диапазон сдвигался на день назад.

## Блокеры из ревью (задокументированы как пилот, требуют решения в прод)

- **Авторизация на клиентских заголовках `X-User`/`X-Roles`** (SSO-заглушка в шлюзе): любой
  клиент может подставить личность/роль. Для пилота — осознанно; в прод — реальный OIDC
  (Keycloak), шлюз сам устанавливает личность из сессии и НЕ принимает её от клиента.
- **Общая БД/`structure_data` у обоих бэкендов** («независимость» не держится на уровне данных):
  vacations сам читает таблицу employees. Для прод — раздельные БД/схемы, либо vacations
  вызывает API сервиса структуры по контракту (вариант из `docs/deployment.md`).

### Безопасность

- ✅ **ИСПРАВЛЕНО** — срок действия сессии (`exp`) теперь проверяется: `_parse_cookie`
  (`shared/auth.py`) отвергает cookie с `exp` в прошлом (`float(data['exp']) < time.time()`).
  Было: проверялось только наличие ключа `exp`, но не время → просроченная `hr_session`
  принималась как валидная.
- **Дублирование `_parse_cookie`** — одинаковая логика парсинга/проверки cookie
  (около 25 строк) в `shared/auth.py` и `services/auth/backend/routes.py`. Точка
  рассинхрона: любая правка (например, фикс выше) нужна в двух местах. Вынести в
  `shared/auth.py` и переиспользовать.
- **Два разных дефолта `AUTH_SECRET`** — кодовый дефолт `'change-me-in-production'`
  (`shared/auth.py`:14, `routes.py`:15) отличается от `hr-auth-secret-change-me`
  в `docker-compose.yml`. Сервис, запущенный вне compose без env, не валидирует
  cookie, выпущенные под compose-секретом (и наоборот). Плюс публично известный
  дефолтный секрет. В прод — один секрет только через env, без кодового fallback.

### Функциональность / баги

- 🟡 **Предупреждение «у коллеги уже отпуск» не срабатывает (мёртвый код)** —
  `services/vacations/frontend/src/VacationsApp.tsx`, `deptOverlap` (стр. 443-454) и
  рендер (стр. 616-620): данные берутся из `items` (вызов `listVacations()` → стр. 403
  → `/api/vacations`), который для сотрудника возвращает ТОЛЬКО его собственные
  заявки (`_list_scope` → `[user.name]`, `vacations.py` стр. 67-71). Поэтому ни один
  `i.employee !== me` не может присутствовать в `items` для рядового сотрудника —
  предупреждение никогда не показывается. Для него нужны данные отдела
  (`fetchDepartment()`, видимость «свои + руководитель»), а не личный список.
- 🟡 **Типы `unpaid`/`study` полуреализованы и «невидимы»** — `VacationIn.type`
  допускает `["annual","unpaid","study"]` (`vacations.py`:59), но `list_vacations`
  фильтрует `WHERE type='annual'` (стр. 84), статистика и таблица тоже считают только
  annual. Не-annual заявки сохраняются, учитываются в лимите 28 и в пересечениях, но
  не отображаются в списке. В `api.ts` `TYPE_LABELS` перечисляет 3 типа, а UI создаёт
  только `annual` (`PLANNED_TYPE`, стр. 380). Несогласованный контракт API↔UI.
- 💭 **Верхний порог `days > 60` недостижим (мёртвая проверка)** — `vacations.py`
  стр. 99-100 допускает до 60 дней в одной заявке, но лимит 28/год (стр. 111)
  отклоняет всё свыше 28 в одной заявке (весь период — один год). Порог 60 вводит в
  заблуждение; фронт уже ограничивает период 28 днями (стр. 492).

### Производительность

- 🟡 **N+1 в `subordinate_tree_names`** — `shared/structure_data.py` (стр. 208-230):
  рекурсивный обход дерева делает по одному `SELECT` на узел в цикле (BFS, по запросу на
  сотрудника). Вызывается на каждый `/api/vacations` (в `_list_scope`/`_visible_scope`).
  **Решение (для сложной структуры компании ~10к человек):**
  - **Короткий путь:** один `SELECT id, name, manager_id FROM employees` (10к строк — это быстро),
    дерево строить в памяти один раз на запрос и обходить итеративно в Python — убирает N+1
    (снижает 10к запросов к 1). Плюс кэш дерева на запрос/секунду.
  - **Правильный путь (SQL):** `WITH RECURSIVE` по `manager_id` (adjacency list) — один запрос на
    всё дерево; добавить индекс на `manager_id` (есть `employees_manager_idx`).
  - **Долгосрочно (масштаб):** closure table / материализованный путь (колонка `path`/`ancestors`),
    поддерживаемый при insert/update, либо хранение «пути до корня» — O(1) поиск предков/потомков;
    при разделении на отдельные сервисы — кэш структуры (Redis) + инвалидация.

## Нагрузка и масштабирование (одновременное планирование тысячами сотрудников + подтверждение руководителями)

Когда сотни/тысячи сотрудников планируют отпуска в один сезон, а руководители массово
подтверждают, узкие места и решения:

- **БД (пул + индексы + pagination):** пул подключений, индексы на `vacations(employee, id DESC)`
  и `employees(manager_id)`, `limit/offset` на `department*`-эндпоинтах (сейчас тянут весь
  отдел), окно по датам. Агрегацию пересечений — одним запросом, не по строке дублируя.
- **Убрать N+1:** перейти на `WITH RECURSIVE` / дерево в памяти (см. запись про N+1) — иначе
  каждый `list/decide` при 10к сотрудников = десятки тысяч запросов.
- **Гонки/лимиты:** 28-дневный лимит и самопересечение — атомарно
  (`INSERT … SELECT … WHERE сумма+days <= 28`, транзакция с `SELECT … FOR UPDATE`/сериализуемой
  изоляцией) + DB-ограничения; иначе при тысячах одновременных вставок лимит просачивается.
- **Очереди (async):** отправка заявок и согласование не должны блокировать запрос — уведомления,
  письма, пересчёты — отложенные задачи (Celery/ARQ + Redis). Подтверждение руководителя —
  быстрый атомарный `UPDATE` по `id` заявки (не тянуть всё дерево на каждый запрос — кэш структуры).
- **Кэш:** структура (дерево/отделы) и результат календаря/пересечений — в Redis с инвалидацией
  (TTL минуты); читаемость при массовом просмотре.
- **Read-model:** остатки (28 дн/год) и пересечения можно материализовать (вью/таблица),
  пересчитывать при изменении, а не считать на каждый запрос.
- **Горизонтальное масштабирование:** stateless-бэкенды (сессия уже в cookie) → k8s HPA по
  CPU/очереди, реплики БД (read), нгинкс-шлюз, Redis для кэша/очередей.
- **Нагрузочное тестирование** (k6/помещение) перед продом: сценарий «N сотрудников создают +
  M руководителей подтверждают», замерить p95 и точки деградации; rate-limit на гейте.
- **Деградация:** при перегрузке — fail-safe на чтение (кэш), уведомления/согласование в очередь
  с retry, запрет на избыточные полные сканы.

## Инфраструктура / сборка / деплой (DevOps-ревью, демо)

Найденные риски по сборке и деплою (не критично для демо, фиксируем для прод):
- **Фиксация версий:** базовые образы плавающие, без digest (`python:3.12-slim`, `node:20-alpine`,
  `nginx:alpine`, `postgres:16-alpine`, `sogaz-auto-chrome:1.6`) — нет воспроизводимости. Пин по digest.
- **Зависимости без версий:** `pip` в backend Dockerfile (`fastapi`, `uvicorn[standard]`,
  `psycopg[binary]`, `psycopg-pool`, `pydantic`) и `e2e/requirements.txt` — каждый сбор ставит latest;
  нужно `==X.Y.Z`/requirements.txt.
- **`npm install` вместо `npm ci`** во всех frontend/shell Dockerfile — не строго по `package-lock.json`.
- **Nexus URL расходятся:** `.npmrc` → `/npm/`, а Dockerfile → `/repository/npm-proxy-registry.npmjs.org/`.
  Привести к одному каноническому.
- **Деплой:** нет `restart`-политик у сервисов; healthcheck только у `db` (у бэкендов/фронтендов/шлюза
  нет); `gateway` зависит от остальных plain-зависимостями (без условия здоровья).
- **`services/auth/frontend` не в npm-workspaces** корневого `package.json` (работает на hoisted-депсах).
- **Безопасность сборки:** нет `USER` (non-root) и `HEALTHCHECK` в Dockerfile; секреты
  (`DATABASE_URL`, `AUTH_SECRET`) в plaintext в `docker-compose.yml` — для демо ок, в бой env/секреты.
- **Шлюз доверяет клиентским заголовкам** `X-User`/`X-Roles` (SSO-заглушка) — при реальном SSO срезать.
- **Хардкод путей** в `scripts/cleanup_test_data.sh` (`DEXE`, `DB_CONTAINER`) и `e2e/run.sh`
  (`--network hr-main_default`) — вынести в env с дефолтом.
