# Фича: «Пересечения отпусков в отделе»

Ветка: `feature/vacation-overlap`
Цель: в сервисе «Отпуска» показать график отпусков сотрудников одного отдела
(из структуры) и пересечения. Руководитель видит свой отдел; сотрудники отдела
тоже видят общий график и пересечения — логично, чтобы не уходили одновременно.

## Декомпозиция (вертикальные срезы, TDD)

Каждый срез — RED (падающий тест) → GREEN (минимальный код) → REFACTOR.
Тесты в `tests/`, команда `python3 -m pytest tests/ -q`.

### T1 — Чистая функция пересечений (без БД)
`find_overlaps(vacations: list[dict]) -> list[dict]` в `backend/overlap.py`
(или в `backend/vacations.py`): возвращает пары пересекающихся отпусков
`{employee_a, employee_b, start, end, days}`.
- Тест: два пересекающихся → найдено; не пересекающиеся → пусто; один → пусто;
  граничные даты (`end1 == start2`) → определено (по умолчанию inclusive = пересечение);
  отпуска одного сотрудника не сравниваются.
- Unit-тест без БД (чистая функция на списке dict).

### T2 — Эндпоинт отпусков отдела
`GET /api/vacations/department` (в `backend/vacations.py`): отпуска всех
сотрудников отдела текущего пользователя (по `employees.department`).
- Тест: пользователь из отдела видит отпуска ВСЕХ сотрудников отдела (общий график);
  пользователь, отсутствующий в `employees` → 404.

### T3 — Эндпоинт пересечений отдела
`GET /api/vacations/department/overlaps`: отпуска отдела + вычисленные пересечения
(через `find_overlaps`).
- Тест: пересекающиеся отпуска → поля `overlaps` непусто; непересекающиеся → пусто;
  структура ответа (отпуска + overlaps).

### T4 — UI в VacationsApp
Секция «Пересечения отпусков (отдел)»: таблица сотрудников отдела по периодам,
подсветка пересечений. Данные из `/api/vacations/department/overlaps`.
- По пирамиде QA: core-логика покрыта backend-тестами (T1-T3); UI — тонкий рендер;
  опциональный Playwright smoke. Без тяжёлой E2E-обвязки.

### T5 — Регистрация/доки
Эндпоинты в `backend/vacations.py` (сервис тот же, `services.json` не меняется).
Обновить постановку/README.

## Решения (согласовать до реализации)
- Какие отпуска учитывать в пересечениях: `pending` + `approved` (плановые) —
  по умолчанию; опционально только `approved`.
- Пересечение = интервалы `[start,end]` inclusive (`end_a >= start_b and start_a <= end_b`);
  касание границ считать пересечением.
- «Отдел» = `employees.department` текущего пользователя; нет отдела → 404.
- Доступ: любой сотрудник отдела видит общий график и пересечения отдела
  (требование: руководитель и сотрудники видят).

## Ревью решения (архитектурно/качество)
Сильное:
- Пересечения вынесены в чистую функцию → переиспользуемо, детерминированно,
  легко проверить (TDD), в проде тот же алгоритм.
- Вертикальные срезы, `find_overlaps` не зависит от БД → быстрые юниты, низ флейк.
- Доступ «весь отдел видит» соответствует требованию; отдел берётся из структуры
  (это и есть «проброс структуры» в отпуска).

Вопросы/риски:
- Отдел = плоское поле `department` (в демо всё HR). В реале — подразделения/дерево:
  уточнить, включать ли дочерние подразделения отдела руководителя.
- Права «любой сотрудник видит весь отдел» — широко; по требованию ок, но отметить.
- Производительность: выборка всех отпусков отдела — ок для демо; в проде
  индексация по `employee`/`department` + пагинация.
- Какой статус учитывать — влияет на смысл «пересечения» (плановые vs подтверждённые).

## Замечания ревью — к исправлению (зафиксировано)

1. **Производительность `find_overlaps`** — сейчас попарный O(n²). Для демо ок.
   При росте отдела (сотни сотрудников/заявок) — перейти на sweep по интервалам
   (O(n log n)) или предварительную индексацию по `employee`/`department`.
2. **Границы inclusive** — сейчас `end_a >= start_b and start_a <= end_b`
   (касание = пересечение). Если бизнес-правило «касание не пересечение» —
   заменить на строгое `>` в одном месте (`_as_date`/`find_overlaps`).
3. **Статусы в пересечениях** — сейчас учитываются все, кроме `rejected`
   (т.е. `pending`+`approved`). Если нужен только `approved` (подтверждённые) —
   сузить фильтр в эндпоинте `/api/vacations/department/overlaps`.
4. **Модель отдела** — сейчас плоское поле `employees.department` (в демо всё HR).
   В реальной оргструктуре уточнить вложенность подразделений (включать ли
   дочерние отделы руководителя) — влияет на выборку «отпуска отдела».
