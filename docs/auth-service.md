# Сервис авторизации/аутентификации (пилот)

Статус: **реализовано (as-built)**. Постановка ниже — как что должно было быть; см. «Замечания».
Backend-фундамент (T0–T4) + frontend (T5) + guard в shell (T6) + смоки (T7) сделаны.

## Цель

Простая аутентификация для пилота: форма входа, 2 учётные записи, после логина —
переход на портал. Управление доступом — **ролями на сотрудниках** (в БД), не по имени:
переназначил роль → изменилась видимость/управление.

## Парадигма

Отдельный независимый сервис `services/auth/` (свой фронт-remote `/mf/auth/` + свой
бэкенд), как structure/vacations. Общие платформенные — шлюз, реестр сервисов.

## Роли (модель из docs/role-model-vacation-planning.md)

Хранятся на сотруднике — колонка `employees.role`:
- `top` — видит все заявки, управляет всеми, создаёт свои.
- `head` — видит свой отдел/подчинённых, согласует отпуска подчинённых, создаёт свои.
- `employee` — создаёт только свои, без согласования (видит коллег отдела, read).

Демо-аккаунты (3 для входа):
- Иван Петров — `top` (Директор по персоналу).
- Алексей Ким — `head` (подчинённый — Сергей Волков).
- Сергей Волков — `employee`.

Остальные сотрудники (Мария — `head`, Ольга) — есть в структуре, логина нет.
Структуру видят **все одинаково (вся)** — намеренно; отделы/вложенность реализованы
(поле `employees.department`, вложенная группировка и сворачивание — см. `docs/structure-departments.md`).
Заметка: сотрудник (`employee`) в «Заявках» видит только свои; в календаре — свой отдел
(свои даты + непосредственного руководителя). Заголовки `X-User`/`X-Roles` (SSO-заглушка для
автотестов) шлюз маппит при отсутствии cookie — в проде их заменяет OIDC.

## Сессия

HttpOnly cookie `hr_session` с подписанным токеном (HMAC по server-secret) — `{name, exp}`.
Роль читается из БД (`employees.role`) на каждом запросе → управляемость ролями.
Без сессии → 401 (портал перенаправляет на форму входа).

## Архитектура

### services/auth/backend (FastAPI)
- `POST /api/auth/login {username, password}` → проверка аккаунта (таблица `auth_users`:
  username, password_hash, employee_id), при успехе — `Set-Cookie: hr_session` (HttpOnly,
  подписанный).
- `POST /api/auth/logout` → сброс cookie.
- `GET /api/auth/me` (и/или `/api/me`) → по cookie: имя + роль (из `employees.role` по
  employee_id), отдаёт `{name, role, department}`.

### shared/auth.py (+ shared/structure_data.py)
- `User.role` (`top|head|employee`), `is_hr` = `role == 'top'` (обратная совместимость).
- `current_user` читает cookie `hr_session`, проверяет подпись, берёт роль из БД.
  Заголовки `X-User`/`X-Roles` (для автотестов/автоматизации) поддержать как fallback.
- `structure_data`: колонка `role` в `employees` + сид ролей; таблица `auth_users`
  (username, password_hash, employee_id) + сид 2 аккаунтов; `role_of(name)`.

### services/vacations/backend + structure
- Видимость/управление отпусков по роли:
  - `top` → все заявки (list, decide все, create свои).
  - `head` → свои + подчинённые (list/calendar отдела, decide подчинённых, create свои).
  - `employee` → свои + коллеги отдела (read), create **только свои** (иначе 403), decide 403.
- Структура (`/api/structure`) — видна вся, одинаково всем (уже так; проверить, что нет
  фильтра по роли).

### services/auth/frontend (remote `/mf/auth/`)
- Форма входа (username+password), подсказка 2 демо-аккаунтов; после успешного логина —
  редирект на портал.
- Кнопка «Выйти» (logout) — в shell.

### services/shell
- При загрузке `/api/me`: если 401 → показать форму входа (auth remote), иначе портал.
- После логина/логаута — перезагрузка/редирект портала.

### platform/gateway
- Маршруты `/api/auth/*`, `/api/me` → backend-auth.
- Прокидывать Cookie `hr_session` к бэкендам (structure/vacations) для `current_user`.
- `/mf/auth/` → frontend-auth.

### services.json
- Запись сервиса `auth` (login-экран; в навигации портала не показывается).

## Замечания

- Пароли пилота — простые, храним hash (для честности), сид: ivan/ivan123, alexey/kim123.
- `services.json` для auth — не показывать в меню сервисов (это логин, не сервис-карточка).
- После рефакторинга тесты conftest переводим с X-User на логин+cookie (через auth service).
- **Проверено as-built:** backend 51 passed (auth + vacations + structure + shared),
  e2e смоки (логин → портал → отпуска → структура → выход + выбор периода).
- **Omp-замечания (исправлено ассистентом):** omp при крупной задаче оставляет типовые
  ошибки — шлюз с прямым `proxy_pass http://backend-*` (теряется ленивый `set $u`-резолв →
  502 при рестарте бэкенда), пропущенный `:` в `if`, чтение куки не по имени `hr_session`,
  `transpileOnly`-обход в webpack (скрывает TS-ошибки). Правило: крупный omp-таск гонять
  по срезам (T0–T7 по отдельности) и валидировать каждый; после — полная проверка сборки/тестов.
- **Сессия:** HttpOnly cookie `hr_session`, SameSite=lax, срок 7 дней; при отсутствии сессии
  `/api/me` → 401, shell редиректит на `/mf/auth/`.

## Видимость отпусков и демо-данные (as-built)

Управление доступом — ролями на сотрудниках (`employees.role`: `top`/`head`/`employee`).
Видимость отпусков (список заявок + календарь/пересечения) — **по иерархическим командам/отделам**
(`_visible_scope`); структура: Иван(top) → Мария(head) → [Алексей(head) → Волков(employee), Ольга(employee)]:
- `top` (корень) — всё дерево (= все).
- Руководитель (есть подчинённые) — свои + дерево подчинённых (Мария: {Мария, Ким, Волков, Романова};
  Ким: {Ким, Волков}).
- Лист-сотрудник — свои + непосредственный руководитель (Волков: {Волков, Ким}), т.к. они в одном отделе.
- Согласование: `top` — все; руководитель — только подчинённые (дерево), в т.ч. «вышестоящий за
  нижестоящего»; `employee` — 403. Заявка вне структуры → 422, пользователь вне структуры → 404.

Планирование — **только Ежегодные** (`type='annual'`): сид и список заявок фильтруются по
`type='annual'` (не-годовые из сида не показываются). В сиде 5 ежегодных заявок с примерами
пересечений: Иван (янв), Мария (март) ↔ Ольга (март), Алексей (май) ↔ Волков (май).

Демо после входа:
- **Иван Петров** (`ivan`/`ivan123`, `top`) видит 5 заявок (свои+подчинённые).
- **Алексей Ким** (`alexey`/`kim123`, `head`) видит 2 (своя + Волкова); в календаре у него пересечение
  Ким ↔ Волков.
- **Сергей Волков** (`volkov`/`volkov123`, `employee`) — создаёт свою заявку на ежегодный отпуск и
  видит в «Заявках» только свои; в календаре — свой отдел (свои даты + руководителя Кима).
  Его заявки видят Ким (линейный руководитель) и Петров (вышестоящий).

Замечание: тесты-фикстуры используют реальных сотрудников структуры (создание заявок вне
структуры запрещено); из-за append-only и лимита 28 дн тесты опираются на авто-уникальные даты
(`make_vacation`).
