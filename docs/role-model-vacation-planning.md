# Ролевая модель и классическое планирование отпусков

Статус: **план** (постановка для разработки). Пользователь вернётся и проверит.
Основано на стандартных практиках HR-систем управления отпусками (иерархическая оргструктура,
delegated approval, календарь отдела, квоты/лимиты). Внешний поиск статей был недоступен —
содержание по общепринятым подходам.

## Цель

Ролевая модель классического планирования отпусков:
- **Топ-руководители** — видят всю структуру компании.
- **Руководители отделов** — видят свой отдел (и подчинённых), согласовывают их отпуска.
- **Сотрудники** — видят **только своих коллег** (свой отдел) и планируют **только свои** отпуска.

## Роли

| Роль | Видит структуру | Видит отпуска | Создаёт/правит | Согласует |
|---|---|---|---|---|
| **Топ-руководитель** (`top`) | всю (все подразделения) | все | свои | все (или через руководителей) |
| **Руководитель отдела** (`head`) | свой отдел + своих подчинённых | свой отдел | свои | отпуска своих подчинённых |
| **Сотрудник** (`employee`) | только свой отдел (коллеги) | коллег своего отдела (read) + свои (полный) | **только свои** | нет |

> Календарь/пересечения считаются для отдела: сотрудник видит календарь своего отдела,
> руководитель — своего отдела, топ — всей компании (или по подразделениям).

## Модель оргструктуры

- Иерархия: Компания → Директорат → Департамент → Отдел → Сотрудник.
- В демо — линейная (у каждого сотрудника `manager_id`), но модель должна позволять
  **вложенные отделы** (отдел может быть у подразделения). Поля сотрудника:
  `id, name, position, department (id/название), manager_id, role (top/head/employee)`.
- Отдел = группа сотрудников с общим `department`; у отдела есть руководитель (`head`).
- Подчинённые руководителя = сотрудники его отдела (и вложенных отделов, если есть).

## Правила планирования (классика)

1. **Сотрудник** планирует **только свой** отпуск (создаёт/правит/удаляет свои). Тип для
   планирования — **Ежегодный**. Не может создавать заявки за других.
2. **Руководитель отдела** согласовывает (принимает/отклоняет) отпуска **своих подчинённых**;
   не может по чужим/вышестоящим. Ведёт календарь своего отдела.
3. **Топ-руководитель** видит отпуска всех; может согласовывать всех (или делегировать
   руководителям отделов). Видит общий календарь.
4. **Пересечения** — внутри отдела: подсвечиваются конфликты; руководитель видит весь отдел
   и решает. Сотрудник видит коллег своего отдела.
5. Только 2027 (для пилота), лимит **28 дн/сотрудник/календарный год**, дедуп пересечений.
6. Рабочее правило: «свой отпуск» — `employee` создаёт под своим именем; сервер обязан
   проверять, что заявка создаётся за текущего пользователя (правило: имя из X-User).

## Матрица прав (детально, для автоматизации)

```
Функция                            | top | head | employee
-----------------------------------|-----|------|---------
GET /api/structure                 | вся | отдел | свой отдел
GET /api/vacations                 | все | отдел | свои + коллеги (read)
GET /api/vacations/department      | все | отдел | свой отдел
GET /api/vacations/department/calendar| все | отдел | свой отдел
POST /api/vacations (заявка)       | свои| свои | ТОЛЬКО свои (иначе 403)
POST /api/vacations/{id}/decision  | все | подчинённые | 403
```

## Планирование (TDD-срезы, постановка)

- **T0 — роль и оргструктура**: `employees.role` (top/head/employee) + вложенные отделы
  (`department_id`, `parent_department_id`), seed с топом/руководителями/сотрудниками.
- **T1 — scope видимости**: сервисный `scope(user)` → подмножество структуры/сотрудников
  (top=все, head=отдел+вложенные, employee=свой отдел). Эндпоинты структуры/отпусков отдают
  только по scope.
- **T2 — «только свои» при создании**: `POST /api/vacations` — если заявитель не
  top/head и заявка не «на себя» → 403 (планировать только свои).
- **T3 — согласование руководителем**: `decision` — head может решать по подчинённым, не по
  чужим/выше (403); top — по всем.
- **T4 — календарь/пересечения отдела по видимости**: `calendar`/`overlaps` отдают отпуска
  видимого отдела (для employee — свой отдел).
- **T5 — UI**: вкладка/страница отпусков по роли; сотрудник видит календарь отдела и создаёт
  только свою заявку; head — блок согласования подчинённых; top — вся структура.
- **T6 — тесты матрицы прав** (как в demos-персонажах; расширить на top/head/employee).

## Вопросы для уточнения (проверит пользователь)

- Сотрудник видит отпуска коллег **только своего отдела** или всей компании (read)? (предположение: своего отдела).
- Топ-руководитель согласует **всех** или только прямых подчинённых? (предположение: всех, либо делегирует).
- Сколько уровней иерархии для демо (2–3) и как выглядит департамент/отдел.
- Нужны ли роли-операторы (HR), кто видит/управляет всеми и кем подтверждено.
